01 System at a glance

The Angular app is served as static files and talks only to /api — through a dev proxy locally, same-origin in production. Spring Boot owns all logic and data; a single Postgres instance holds every table. There are two outbound dependencies: SMTP for email, and Open-Meteo for the next-run weather forecast.

03 Backend, by domain

Code under ro.threet.run is organised by domain, not by layer — each package carries its own entity, repository, service, controller, and DTOs. Cross-cutting concerns (web, config) sit apart. Where two domains would depend on each other, the dependency is inverted. event owns a RegistrationCounts port, and registration implements it. event publishes EventCancelled and EventRescheduled, and the notifiers in registration listen for them.

04 Data model

Two seams are deliberately built into the schema now (charter §3): location is a first-class entity, and registration is stored in a leaderboard-friendly shape — one row per (event, participant) with finish_time and user_id nullable. The leaderboard-friendly shape has already paid off. Finish-time entry, the leaderboards and personal stats (Increments 11–13) needed no change to the registration table. Later migrations only added things: names on accounts, coordinates on locations, roles, and an event status.

Why nullable everywhere it counts. An anonymous registration carries name + email with a null user_id; a signed-in one is attributed to the account. A runner's own result writes into finish_time. Neither needed a schema change, because the columns were there from V3.
Cancel, don't delete. A cancelled event keeps its registrations (ADR-0001). The (status, start_datetime) index serves the public list, which leaves out cancelled runs.

05 The core loop

Register for a run, get a confirmation email

The riskiest, most valuable path — and it stays anonymous. If the caller happens to have a session, the registration is quietly attributed to their account; if not, user_id is null. Either way, one email goes out.

06 Event lifecycle

Admins manage runs; registrants are told about changes

Admins create, edit, delete and cancel runs under /api/admin/**. Delete and cancel are different actions on purpose (ADR-0001), so removing a run never silently destroys other people's data.

07 API & security

Deny-by-default, with the public surface enumerated

Authorisation is deny-by-default in SecurityConfig: anything not listed is authenticated(), so a new endpoint is closed until deliberately opened. A protected hit without a session is a plain 401 — this is an API; the SPA owns the login UI. /api/admin/** needs ROLE_ADMIN, and a signed-in non-admin gets 403. The server enforces this boundary; hiding the admin controls in the UI is only a convenience.

08 The seams

Each external dependency, and the one cross-domain dependency, sits behind an interface. So a provider can change without edits across the app, and tests can use a stand-in.

Auth

Everything above AuthProvider deals in AccountPrincipal — never in the users table or BCrypt. Credential logic and session mechanics are split so an OIDC provider that manages its own session drops in without edits across the app.

  • AuthProvider — credential logic only. Today's one implementation is LocalAuthProvider (email + BCrypt on app_user). A future Entra provider is a new AuthProvider + a SecurityConfig change, not edits across the app.
  • SessionAuthenticator — session mechanics live in the web layer, kept out of the provider, so a provider that owns its own session slots in cleanly.
  • AccountPrincipal — the currency above the seam. The rest of the app knows this, not rows or hashes.
  • Registration linkage — POST /api/registrations stays anonymous, but a session attributes the row to its account; a signed-in registration form prefills from the account (still editable).
  • Roles — RoleService checks the roles against ADMIN_EMAILS each time a user signs up or logs in. Every account has ROLE_USER. An account named in ADMIN_EMAILS gets ROLE_ADMIN, and an account that is no longer named loses it. The variable is empty by default, so a new deploy has no admins.

The other seams

  • WeatherProvider — takes a coordinate and the run's local date and time, and returns an Optional<Forecast> for that hour. OpenMeteoWeatherProvider calls Open-Meteo's hourly forecast. CachingWeatherProvider wraps it in a Caffeine cache (WEATHER_CACHE_TTL, default 1 h), so most page views make no upstream call. A run beyond WEATHER_FORECAST_HORIZON_DAYS (default 8) has no forecast.
  • EmailSender — SmtpEmailSender sends to Mailpit in dev and tests, and to a transactional provider in prod. The confirmation, cancellation and reschedule emails are plain message types in registration.
  • RegistrationCounts — the only thing event needs to know about registrations is a count. It is a port that event owns and registration implements. The names and addresses of registrants never cross it.

09 Testing & the release gate

Acceptance-test-driven RAD

Requirements stay thin on purpose; rigour goes into tests. Six core E2E scenarios (CS-1…6) are the release contract — green before every release.

Definition of Done (charter §6). Vertical slice complete · new logic unit-tested · endpoint integration-tested against real Postgres · affected CS scenario updated · axe-core clean at mobile + desktop · CI green · merged to main, incomplete work behind a feature flag.
