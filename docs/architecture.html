01 System at a glance

The Angular app is served as static files and talks only to /api — through a dev proxy locally, same-origin in production. Spring Boot owns all logic and data; a single Postgres instance holds every table. Email is the one outbound dependency.

03 Backend, by domain

Code under ro.threet.run is organised by domain, not by layer — each package carries its own entity, repository, service, controller, and DTOs. Cross-cutting concerns (web, config) sit apart.

04 Data model

Two seams are deliberately built into the schema now (charter §3): location is a first-class entity, and registration is stored in a leaderboard-friendly shape — one row per (event, participant) with finish_time and user_id nullable. Both make V2 additive, not a migration.

Why nullable everywhere it counts. An anonymous registration carries name + email with a null user_id; a signed-in one is attributed to the account. V2 results write into finish_time. Neither needs a schema change — the columns already exist.

05 The core loop

Register for a run, get a confirmation email

The riskiest, most valuable path — and it stays anonymous. If the caller happens to have a session, the registration is quietly attributed to their account; if not, user_id is null. Either way, one email goes out.

06 API & security

Deny-by-default, with the public surface enumerated

Authorisation is deny-by-default in SecurityConfig: anything not listed is authenticated(), so a new endpoint is closed until deliberately opened. A protected hit without a session is a plain 401 — this is an API; the SPA owns the login UI.

Session, not a token in JS. An httpOnly JSESSIONID cookie — SameSite=Lax, Secure on by default (dropped only for local http). Rotated on login (fixation defence). Spring's CSRF tokens are off: the API is same-origin and SameSite=Lax blocks the cross-site form POST, keeping the anonymous registration token-free. A token-based CSRF layer is a tracked pre-go-live hardening item.

07 The auth seam

Everything above AuthProvider deals in AccountPrincipal — never in the users table or BCrypt. Credential logic and session mechanics are split so an OIDC provider that manages its own session drops in without edits across the app.

  • AuthProvider — credential logic only. Today's one implementation is LocalAuthProvider (email + BCrypt on app_user). A future Entra provider is a new AuthProvider + a SecurityConfig change, not edits across the app.
  • SessionAuthenticator — session mechanics live in the web layer, kept out of the provider, so a provider that owns its own session slots in cleanly.
  • AccountPrincipal — the currency above the seam. The rest of the app knows this, not rows or hashes.
  • Registration linkage — POST /api/registrations stays anonymous, but a session attributes the row to its account; a signed-in registration form prefills from the account (still editable).

08 Testing & the release gate

Acceptance-test-driven RAD

Requirements stay thin on purpose; rigour goes into tests. Six core E2E scenarios (CS-1…6) are the release contract — green before every release.

Definition of Done (charter §6). Vertical slice complete · new logic unit-tested · endpoint integration-tested against real Postgres · affected CS scenario updated · axe-core clean at mobile + desktop · CI green · merged to main, incomplete work behind a feature flag.
